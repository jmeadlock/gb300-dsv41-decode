# C2C probe — recipe A's thesis, first numbers (2026-11-06, `bench/c2c_probe.py`, receipt `c2c-probe-gb300-20261106.json`)

Measured on the GB300 in the library image, real expert bytes (`layers.0.ffn.experts.0.w1`), box otherwise idle.

| what | measured |
|---|---|
| `cudaHostRegister` of an exact-size anonymous mmap (1 GiB) | 0.148 s → **7.3 GB/s** (189 GiB Engram ≈ 28 s; 62 GiB cold pool ≈ 9 s) |
| copy engine H2D from registered host, 1 GiB bulk | **390 GB/s** |
| copy engine H2D at expert granularity (36 × 18.8 MB, one stream) | 366 GB/s, **52.5 µs per expert**, 1.85 ms for 36 |
| kernel reading host-mapped memory directly (`torch.sum` over the UVA view) | 230 GB/s (same naive kernel on HBM: 361 GB/s — the kernel is the limit, not the link) |
| reference `fp4_gemm`, weights in HBM vs weights as a UVA view of registered host memory, M=1 / M=6 | 91.3 → 102.8 µs / 91.1 → 102.9 µs; **outputs bit-identical** (`torch.equal`) |
| Engram-style gather, 24 random 264-B rows from a 1 GiB table, UVA vs HBM | 15.7 µs vs 14.2 µs (the lane's measured 0.04 ms Engram gather is consistent) |

## What it says

1. **The UVA path is correct and cheap to set up.** A reference kernel reads registered Grace memory through the same code path as HBM and produces identical bits; registration costs seconds, not minutes. The plan's §5(b)(c) mechanism works as written.
2. **The reference `fp4_gemm` is latency-bound, not bandwidth-bound** (91 µs for a 5.9 MB weight from HBM = 64 GB/s effective; 18 CTAs at M=1). That is why UVA costs only +11.5 µs on it. With a bandwidth-efficient kernel (DeepGEMM MegaMoE does ~25 experts in ~79 µs/layer) the Grace read would be exposed: ~50 µs per cold expert at 366–390 GB/s vs ~2–3 µs from HBM.
3. **Recipe A lives or dies on cold-expert bytes per step.** From Pg61's own peer-tier stats on the W0b window (`peer3_stats.json`): at T=6 rows the sidecar saw **2.06 cold experts per layer-call** (1.6 at T=1), i.e. ~80 cold expert reads per 6-row step ≈ **1.5 GB over C2C ≈ 3.9 ms at 390 GB/s** — alone more than the 5.0 ms bar. Pg61's static `rowmap` (295 hot / 89 cold) therefore cannot be recipe A's map.
4. **The map that makes recipe A possible already exists in our own research**: the adaptive-residency work (v26 "seeded adaptive", `Ideas/Inference - Expert Residency.md`) measured the frozen static map at a 17–28 % cold share (7–11.5 cold picks/layer/step) and the seed map + swaps converging to **< 1 % (≤ 0.41 cold picks/layer/step)** in 9–16 s per workload. At 0.41/layer/step: ~16 cold reads per step ≈ 300 MB ≈ **0.8 ms at 390 GB/s, and the copy engine can run it concurrently with the hot-expert kernels**, versus the sidecar's 1.33 ms exposed `_finish2` wait on v27.

## Consequence for the charter (for James)

Decision 13 ("static map for M0–M2, slot cache deferred") is wrong for recipe A as a *thesis test*: at a static map's cold share the C2C self-fetch loses on bandwidth before any kernel is written. Proposed amendment: M0 keeps the static map (parity only); **M2 = adaptive residency (our v26ar seed-map + swap policy, ported into the runtime) + C2C self-fetch of the residual cold set**, with the bar stated as cold bytes/step × C2C bandwidth. The sidecar (recipe B) remains the bandwidth-correct design when cold share is high; A wins only when the map is good. Both numbers are now measurable before any fusion work.
