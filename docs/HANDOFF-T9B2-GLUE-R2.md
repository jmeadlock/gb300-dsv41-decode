## The RMSNorm question decides this round — settle it first (desk, then box-verifiable)
torch computes `x.float().pow(2).mean(-1)` with its reduce kernel: for a 5120-wide fp32 row the summation order is a fixed tree (vectorized per-thread partials → warp shuffle → block reduce). A Triton kernel will not reproduce that order by accident. Two acceptable outcomes, state which you achieved per cluster:
- **(i) bit-identical**: reproduce torch's reduction tree for the exact shapes (5120, 2304? — list every normed width in the decode path) — feasible only if you can read the launch configuration torch picks (`reduce_kernel` config for `[1, 5120]` fp32: block/vec sizes) and mirror it; R1's calibration mechanism can *search* a small family of orders (sequential, pairwise tree, 4/8/16-way partials + tree) against torch on 1,024 random rows and pick the one that matches all of them; if none matches → outcome (ii).
- **(ii) GEMV-class drift**: the fused norm differs by ≤ 1 ulp of the fp32 statistic on a small fraction of rows; then the cluster is flag-gated as `fused-approx` (default **off**), measured by the first-light drift row, and the summary names it. **No cluster ships silently non-identical.**
Same for the sinkhorn prologue statistic (#5) and Engram's two rsqrt statistics (#15). The router (#4) and indexer (#14) have a second hazard: **topk ties** — torch's `topk` tie-break on CUDA is by index order within its algorithm; reproduce by selecting with (value, −index) lexicographic compare and verify on tie-heavy synthetic inputs; if torch's order cannot be pinned down, fuse everything *around* the topk and keep torch's topk launch (still saves most of the cluster).
