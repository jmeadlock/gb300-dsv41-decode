## 3. Why the first plan failed (so the second does not repeat it)

- **No control arm.** The bar was Pg61 (two GPUs). The honest single-GPU control, v28-prob, was never booted or cited.
- **A rewrite where a port was available.** Three days went into re-deriving glue, routing, GEMV and prefill that
  vLLM/Garner already had faster; the three things that were new (C2C staging rates, residency inside the step,
  fixed-order determinism) were a fraction of the effort.
- **Memos ahead of measurements**, coders with no GPU, one serialized box.
- **Prior art not read first** — the lane skill held `el8-m3-grace-only.md` and `adaptive-residency-v26ar.md` the whole time.

## 6. How the work runs from here

- **Control arm first.** No card without the existing best recipe measured on the same harness in the same window class.
- **Prior art before design.** Lane skill references + J-M-Recipes + peer repos are read before any "new" claim.
- **Bounding measurement before build** (the mini-test pattern: 2 minutes of box answered a 40-page memo's open questions).
- **I read the code I boot.** Design reads and boot debugging are done by the orchestrator on Fable; workers get
  bounded coding with a stated test, and run as background + notify so their exit re-enters the session.
- **Failure restores the lane automatically** (card-gt1's default), so an orchestrator gap leaves Pg61 up, not dark.
- **Kill rules are written before the card**, as in the table.
