Scope: making a kernel boundary cheaper *without* fusing. The fusion ladder is `docs/M2-FUSED-CHAIN-DESIGN.md` (M2 memo, 03:35 today); where a lever here overlaps a rung there, I say so and do not re-derive it.

## 0. Verdict

The boundary is not idle time between nodes — our graph step already equals the sum of kernel durations — it is the fixed ramp/first-DRAM/tail inside each of ≈ 2,000 short kernels, of which ≈ 0.74–1.1 ms is pure node dispatch [E from sm_120/Ampere rates]. Programmatic Dependent Launch is the only non-fusion tool that attacks it, it works inside `torch.cuda.graph` (stream capture records programmatic edges; vLLM 0.31.0 runs exactly this on our box), and every toolchain in the image exposes it (Triton 3.7.1 `launch_pdl` + `gdc_*`, DeepGEMM `set_pdl` — **off by default at our pin and never called by our runtime**, CuTe DSL `use_pdl`, TileLang `T.pdl_*`), while aten glue, FlashMLA's sparse op and most cuBLAS nodes cannot be PDL secondaries. Done properly — DeepGEMM PDL on, every owned Triton kernel PDL-chained, GEMVs prefetching their weights into L2 *before* `gdc_wait()` (outside loops: Triton 3.7.1 lacks the #11906 pipeliner fix), plus post-capture LaunchCompletion edges for producers we cannot edit — it is worth **≈ 0.45–1.5 ms at 1 row (central 0.8: 10.5 → ~9.7 ms) and about the same absolute at 6 rows**, bit-identical by construction. Published decode gains match that scale (+3 % TPOT where stacks were already fused; ≈ 2 µs/edge, −16 % body, on an unfused H100 chain). It cannot reach 5.0 ms on its own: even at the published PDL floor each dependent edge costs 0.37–1.15 µs, so 5.0 ms (≈ 0.4 ms above the 4.6 ms bandwidth floor) admits only ≈ 350–1,080 edges per step — the node count must fall 2–6× (M2 ladder / persistent stretch) and the PDL recipe must be built into every new kernel. Graph-level knobs are not levers: replay CPU cost is constant, device launch adds nothing per node, and conditional nodes cost ≈ 8 µs per dispatch (use in-kernel predicates instead).

## 1. Findings with citations

### 1.1 What "the boundary" actually is in our step (reframing, important)

- Our graph step equals the sum of kernel durations: Σ CUPTI durations 13.91 ms vs graph step 13.88 ms at the 13.9 ms anatomy [M, `step-anatomy-r2-20261107.json`, quoted in M2 memo §0.3]. So there is **no measurable idle gap between graph nodes**; the per-launch cost lives *inside* each kernel's duration: grid dispatch + CTA admission, prologue, the first DRAM round trip, and the drain/tail of the last CTAs.
- The kernel count at 10.52 ms is ≈ 2,000, not 2,800 (M2 memo §0.1 [E]: 1,742 ops in the CPU census + GPU sub-kernels). I use **2,000 nodes at 1 row** below; at 6 rows the count is about the same (M2 §1: "~80 % of the step stays flat in time").
- Published per-boundary costs on Blackwell (none on GB300 / sm_103):
  - Empty kernels in a CUDA graph: **428 ns** node-to-node; PDL chain of empty kernels: **366 ns**; all-SM counter barrier 663 ns; all-SM gather with data 1.0–1.15 µs; under a real DRAM weight stream (dependent 4096² bf16 GEMV chain) **0.74–1.06 µs exposed per boundary with dynamic row claiming, 1.2–2.3 µs with fixed tiles, 2.85–3.23 µs when the stream stops at each boundary** [C, Bojie Li, RTX PRO 6000 sm_120, 188 SMs, 2026-09-26, https://github.com/bojieli/ai-infra-book/blob/main/calculations/sources/opentallas/blackwell-sync-latency-notes.md].
  - NVIDIA: repeat-launch *device* runtime of a straight-line graph of 1,025 nodes = 567 µs (CUDA 12.6; ≈ 0.55 µs/node), CPU-side repeat launch ≈ 2.5 µs + ~1 ns/node for ≥ 10-node straight-line graphs (Ampere) [C, NVIDIA blog 2024-09-11, https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements].
  - H100 Llama-3.2-1B, the Hazy megakernel split into 81 graph kernels: default graph edges cost **190 µs over 79–80 boundaries (≈ 2.4 µs/boundary)** vs the persistent VM; PDL with *early trigger + producer-independent loads before the wait* recovers 154–158 µs (82.8 %, ≈ 2.0 µs/edge) [C, tie-pilot-qxw, 2026-08-04/05, https://github.com/tie-pilot-qxw/pdl-megakernel-reconstruction/blob/main/docs/reconstructing-a-megakernel-with-pdl.md].
- Reading: the *pure dispatch* part of a boundary is ~0.4–0.55 µs/node → **≈ 0.8–1.1 ms of our 10.52 ms** is node dispatch alone [E: 2,000 × 0.37–0.55 µs; sm_120/Ampere numbers, GB300 unmeasured]. The rest of our ~5 µs mean kernel is ramp + first-DRAM + tail + latency-bound work. PDL attacks dispatch + prologue + first-DRAM (only where the consumer has producer-independent loads, i.e. weights) + some tail (successor CTAs fill SMs vacated by a straggling predecessor: the "rolling tail wave" seen with `%globaltimer`/`%smid` in the H100 study). It cannot remove the dependency itself (≈ 0.37–1.15 µs per edge on sm_120).

### 1.2 PDL mechanics and whether it works inside our captured graphs

- API: secondary launched with `cudaLaunchAttributeProgrammaticStreamSerialization`; primary calls `cudaTriggerProgrammaticLaunchCompletion` (`griddepcontrol.launch_dependents`), implicitly at block exit if it never does; secondary must call `cudaGridDependencySynchronize` (`griddepcontrol.wait`) before reading primary output. Overlap is "opportunistic and not guaranteed" [C, CUDA Programming Guide 13.5 §4.5, https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html, fetched 2026-11-07].
- **In CUDA graphs**: PDL works "via stream capture or directly via edge data". Stream capture of a PDL launch produces an edge `{type = cudaGraphDependencyTypeProgrammatic, from_port = cudaGraphKernelNodePortProgrammatic}`; a `cudaLaunchAttributeProgrammaticEvent{triggerAtBlockStart=1}` maps to `from_port = cudaGraphKernelNodePortLaunchCompletion` ("activates when all blocks of the kernel have begun execution") [C, same §4.5.3; port definitions in CUDA Runtime API types, https://docs.nvidia.com/cuda/archive/13.3.1/cuda-runtime-api/group__CUDART__TYPES.html]. So `torch.cuda.graph` (stream capture only, https://docs.nvidia.com/dl-cuda-graph/latest/torch-cuda-graph/torch-integration.html) records programmatic edges for any kernel launched with the attribute. No special graph flag is needed.
- Production evidence on *this image*: vLLM 0.31.0's DSV4.1 code launches Triton kernels with `launch_pdl=` and `tl.extra.cuda.gdc_wait()/gdc_launch_dependents()` (`reference/vllm-0.31.0/deepseek_v41/common/ops/query_quant.py:40-46,108,126` [L]), CuTe DSL kernels with `use_pdl=True` and `cute.arch.griddepcontrol_wait()` (`deepseek_v41/nvidia/ops/fused_wo_a.py:228-233,498` [L]), and turns DeepGEMM PDL on globally (`reference/vllm-0.31.0/utils_deep_gemm.py:217-230,288-290` [L]) — all inside vLLM's FULL CUDA graphs, which are torch-captured. The Pg61 lane runs PDL + FULL graphs on this same box (round-1 W1 lane recap, `~/hermes/research/dsv41-catchup-6000-20261027/r6-outside-view/W1-megakernels.md:5`). So "PDL under torch capture" is proven on GB300 in production; it is unproven only in *our* runtime.
- torch 2.13 (our image) has `torch.cuda.CUDAGraph(keep_graph=True)`, `raw_cuda_graph()`, `raw_cuda_graph_exec()`, `instantiate()` [C/L: `torch/cuda/graphs.py` at tag v2.13.0 lines 82-107, 173, 217-224, fetched via `gh api` 2026-11-07]. This allows editing captured edges (e.g. upgrading a normal edge to a programmatic LaunchCompletion edge) before instantiation — see §1.8.

### 1.5 Graph node count vs replay cost; device launch; conditional nodes

- Replay CPU cost is ~constant for straight-line graphs (2.5 µs + ~1 ns/node, CUDA ≥ 12.6) [C, NVIDIA 2024-09-11]. Our step is one graph replay/step, so host cost is ~5 µs/step and hidden if the host runs ahead. **Not a lever.**
- Device-side cost scales with nodes: ≈ 0.55 µs/node (Ampere, 12.6 blog) / 0.43 µs/node (sm_120 empty-kernel graph gap) [C]. For our 2,000 nodes: 0.86–1.1 ms of dispatch [E]; it shows up inside kernel durations, not as gaps (§1.1). Only fewer nodes (fusion) or overlapping dispatch with the predecessor (PDL) removes it.
- Device graph launch (`cudaGraphInstantiateFlagDeviceLaunch`): moves *launching* to the device; no per-node gain. Useful only to keep a draft→verify→accept loop off the host [C, https://developer.nvidia.com/blog/enabling-dynamic-control-flow-in-cuda-graphs-with-device-graph-launch/]. CUPTI 13.2/13.4 early-attach makes `cudaGraphLaunch` of conditional-node graphs block until other streams idle (forum report, 2026) — profiling artefact to remember.
- **Conditional nodes are not cheap**: a producer kernel selecting one of two follow-up kernels costs 12.3 µs with a conditional graph vs 4.1 µs fixed graph → **≈ 8.2 µs per conditional dispatch** (vs 15.0 µs via host copy-and-branch) [C, arXiv 2607.23099v3 Table III, B200/FlashInfer, 2026-07]. So an IF node to skip our 9.2 µs `t9a2_stage_inplace` when a layer has no cold rows would save ≈ 1 µs at best. **Use a device-predicated early exit inside the kernel (or fold staging into the MoE prologue, M2 L7) instead.** A WHILE node for the speculative loop is only worth it if the host loop shows gaps (see next point).
- Host-loop discipline for T12 (DSpark loop): LMSYS found 47 % GPU idle at batch 1 with DSpark (10.62 ms step, 4.99 ms idle) — *not inside graphs* (in-graph micro-gaps ≈ 80 ms per 3 s) but in 4–5 eager gaps/step of 100 µs–2 ms caused by blocking `.to("cpu")` reads between draft and verify graphs [C, LMSYS 2026-08-21]. Our M1-T12 loop must never block the host on a device value between graph replays; acceptance stays on device and the next graph is enqueued before the host knows it.

### 1.6 Kernel-size floors on sm_100/103

- No published in-graph launch-to-launch microbenchmark on sm_100 or sm_103 found (searched 2026-11-07). Best public: sm_120 428 ns (graph gap, empty kernels), 366 ns (PDL chain), L2 round trip 117–146 ns, fence after store ~250 ns [C, Bojie Li]. GB300 is two dies with split L2; cross-die boundaries are plausibly slower (unverified, no public number).
- A B200 agent-memory note reports 1-kernel graph replay ≈ 9.3 µs end-to-end host-timed, back-to-back stream launches 6.5–8 µs, event resolution ~2 µs [C, low quality: HF dataset Infatoshi/kernelbench-cuda-traces, 2026-07-19]. These are host-inclusive and not node-to-node; do not use for modeling.
- Our own floor evidence: the ~700 aten glue kernels average ~2 µs and a 2 MB read takes the same time as an empty kernel at that size [M, `STEP-ANATOMY-R2-20261107.md:10`; the B200 note says the same for 0.5–2 MB reads]. So **~2 µs is the practical floor of a non-PDL dependent kernel on this box today; ~0.4–1 µs is the floor of a PDL-chained one** [E from sm_120 numbers]. The gap between the two, times the edges we can convert, is the PDL budget.

### 1.7 nvjet / cuBLAS small-M vs a handwritten GEMV

- TRT-LLM #20634 (Vera Rubin, DSV4.1-Flash, CUDA-graph replay, weights rotated past L2): for `wq_a` 1280×5120 and `wkv` 512×5120 bf16, "cuBLAS picks 16x64 / 32x64 nvjet tiles … reaches only 0.9–2 TB/s"; nvjet 6.64 / 5.86 µs vs `trtllm::tinygemm2` 3.85 / 3.67 µs at M=1, "M=4 and 6 behave the same"; concatenated [wq_a; wkv] 4.13 µs vs 12.5 µs for the two cuBLAS calls; step 5.97 → 5.70 ms TP4 [C, 2026-10-19].
- Our nvjet nodes: 40 × 14.5 µs = 0.58 ms on mHC/gate-class tiny mms [M, R2 anatomy]; cuBLAS mm on these shapes is often **two kernels** (`dot` + `reduce_1Block`, 80 launches for the mixes) [M, M2 memo §1]. A handwritten GEMV is one launch, row-invariant by construction, and PDL-capable — which is a launch-boundary argument on top of W3's bandwidth argument. The replacements themselves are M2 rungs L1/L2/L4/L9 (A3 unless calibrated); W3 owns the GEMV kernel design. Not re-derived here.
- vLLM #34302 "Add TRTLLM DSV3 Router GEMM kernel (6 % B1 speedup)" and onnxruntime #32289 (H200: 10–17 % lower median latency at M=1 vs cuBLAS, but up to 7.3× slower at M ≥ 8) [C, titles/summaries only] — small-M custom kernels win at M ≤ ~6 and lose beyond; at our 1–6 rows they win.

### 1.8 Non-obvious lever: post-capture programmatic edges with the LaunchCompletion port

- Problem: a PDL consumer only overlaps its pre-wait work with what comes *after* its producer's trigger. Producers we cannot edit (aten glue, cuBLAS, FlashMLA, TileLang oracle kernels, DeepGEMM sm100 — none trigger early) trigger implicitly at exit, so the consumer's pre-wait weight loads only overlap the memory flush.
- CUDA graphs let the *edge* carry the trigger point: `from_port = cudaGraphKernelNodePortLaunchCompletion` activates the edge "when all blocks of the kernel have begun execution", no kernel code required [C, CUDA §4.5.3 + Runtime API port definitions]. With torch 2.13 `keep_graph=True` + `raw_cuda_graph()` we can, after capture and before `instantiate()`, replace selected `A → B` edges by programmatic LaunchCompletion edges **where B is one of our PDL kernels that calls `gdc_wait()` before every dependent read in every CTA**. Then B's CTAs are admitted as soon as A's last CTA has started (single-wave A: almost immediately), stream B's weights while A runs, and wait for A's full completion + flush before touching A's output.
- Requires cuda-python (`cuda.bindings.runtime.cudaGraphGetEdges_v2 / cudaGraphRemoveDependencies_v2 / cudaGraphAddDependencies_v2`) in the image — unverified (probe P4). Risk: B's resident CTAs compete with A for SMs/regs/SMEM; at decode shapes A is sub-wave so this is expected to help (Ling: "at decode shapes it is pure gain"), but it is not guaranteed and must be measured. Nobody publishes this exact trick for LLM decode that I could find (searched 2026-11-07); it is standard CUDA graph API, so it is "unverified in practice", not speculative in semantics.

### 1.9 Correctness rules for any PDL work (all bit-identical when followed)

1. Every PDL-launched kernel executes `gdc_wait()` in every CTA before its first read of any producer output **and before it exits** — even if it does not read the predecessor's output. Otherwise transitivity breaks: A → B(PDL, never waits, finishes early) → C(PDL) reading A's output waits only on B (CUDA PG: the secondary "must always use `cudaGridDependencySynchronize`") [C + E].
2. Trigger placement: `gdc_launch_dependents()` may go anywhere *after the kernel's own `gdc_wait()`* (Ling: moved triggers to right after the producer's own wait) — it releases launch only; consumers' waits still fence on full retirement [C, LMSYS 2026-08-21]. Never trigger before your own wait in a kernel that **spins on a flag written by another stream/host** (successor CTAs can occupy the SMs the flag-writer needs → hang; project-maya #495, round-1 W1 §1.8).
3. Triton 3.7.1: `gdc_wait()` outside loops only (bug #11905, fix #11906 not in 3.7.1); no `warp_specialize` on PDL kernels (#12395).
4. TMEM: a kernel that allocates TMEM before its wait can stall behind a TMEM-holding PDL predecessor on the same SM (vLLM `fused_wo_a.py:231-232` comment says "allocating earlier can deadlock") [L]. DeepGEMM sm100 allocates before its wait (`sm100_fp8_fp4_gemm_1d1d.cuh:186-195`) [L]; vLLM nevertheless runs DG with PDL on globally in production, so the DG→DG case is exercised; our DG predecessors are Triton kernels (no TMEM).
5. cuBLAS ≥ 13.1.0 device-pointer alpha/beta WAR hazard (CUB-10409) — keep alpha/beta on host for any cuBLAS node behind a PDL producer.
6. Grading: PDL is scheduling only; with orders unchanged outputs are bit-identical (Ling 4/4 bitwise; TRT-LLM 0/20,000 mismatches). Grade every PDL change with **many-replay stress, new input per replay, bitwise vs PDL-off** (the #20634 method), not one replay.

**Sum of B1–B6: ≈ 0.45–1.5 ms at 1 row (central ≈ 0.8 ms, i.e. 10.5 → ~9.7 ms), ≈ 0.4–1.4 ms at 6 rows** [E]. That overlaps M2's L5 (0.35–1.0 ms) — B2+B3 *are* L5, now with a concrete kernel recipe and evidence; B1, B4, B5-as-predicate, B6-extra, B8 are new. Do not add B2+B3 to M2's total twice.

What PDL cannot do: it keeps every node and every dependency. With ≈ 2,000 nodes the dependency floor alone is 0.74–2.3 ms (0.37–1.15 µs/edge, sm_120). Against the 5.0 ms bar and M2's 4.6 ms bandwidth floor, the step can afford only **≈ 350–1,080 dependent edges** even at the published floor (§2 last row). So: PDL is necessary and cheap, but the bar also requires the node count to fall ~2–6× (M2 ladder → ~700; persistent stretch → ~170). PDL's value *per remaining edge* grows as kernels get bigger (more producer-independent weight bytes to prefetch), so B3's recipe should be built into every M2 rung, not bolted on after.

Numerics class for all of §3: **bit-identical**, graded by many-replay stress (new input per replay, bitwise vs PDL-off), never by one replay.
